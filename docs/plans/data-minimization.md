# Минимизация данных во внешних запросах и диагностике

Статус: реализация по согласованному поручению пользователя. Отдельная ветка и PR, без merge/deploy.

## Согласованный объём

- Удалить исходные данные рождения, названия карт и идентификаторы аккаунта из структурированного контекста ИИ. Передавать только необходимые астрологические данные и содержание самого обсуждения.
- Исключить тела запросов/ответов, заголовки, полные URL и содержимое карт/чатов из логов приложения и Langfuse. Оставить безопасное имя операции, статус, длительность и случайный ID отдельного вызова.
- Проверить/ограничить исходящий Astrology payload только расчётными полями: дата, время, координаты, timezone и конфигурация. Email, ник, account/user/chart/client ID не передавать.
- Сохранённые карты, данные рождения, почта и переписка в БД остаются; истории обсуждений доступны пользователю. Схему авторизации не менять.

## Границы

Это минимизация данных, а не гарантия анонимности или соблюдения 152-ФЗ. Astrology API по-прежнему получает исходные данные, необходимые для расчёта. Астрологические положения могут косвенно раскрывать время рождения. Пользователь может сообщить личную информацию в вопросе, сохранённой переписке или тексте трактовки: свободный текст не подвергается ненадёжному автоматическому «обезличиванию».

Старые логи, traces, внешние копии и production-БД не удаляются автоматически. Перенос базы в РФ, правовые документы, сроки хранения и удаление аккаунта — отдельные задачи. Логи инфраструктуры и политики внешних провайдеров требуют отдельной проверки.

## Проверки

Маркеры имени/email/даты рождения/account ID в лишних структурированных полях не должны появляться в AI-контексте или диагностике. Расчётные поля, аспекты и текст вопроса сохраняются. Логи не должны читать тело запроса/ответа даже при API_LOG=true. Langfuse получает только метаданные, включая ошибочные вызовы без текста ошибки. Сбой диагностики не должен терять успешный ответ ИИ. Внешний Astrology payload строится явной проекцией без лишних полей.
