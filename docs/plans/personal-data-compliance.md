## Auth: Telegram + email

### Сущность User (цель)

- `telegramId` — optional, unique sparse.
- `email` — optional, unique sparse (lowercase).
- `passwordHash` — optional (не обязателен для входа).
- Хотя бы одно из: `telegramId` или `email`.
- Имя / birthPreferences — как сейчас.

### Связь способов

1. Регистрация/вход через Telegram Login Widget → сессия; если email ещё нет — можно привязать позже в профиле.
2. Регистрация/вход через email → код на почту (OTP) → сессия; в профиле — «Привязать Telegram».
3. Один человек = один User; привязка второго способа по сессии владельца (не создавать дубликат).
4. Конфликт (email уже у другого User / telegramId занят) — ошибка, без автослияния.

### Пароль vs код на почту

| Вариант | Плюс | Минус |
|---------|------|-------|
| Только пароль (как сейчас) | Работает без SMTP | Надо помнить; сброс всё равно нужен |
| Только код на email | Не помнить пароль | Спам/задержки → «не входит» |
| Только Telegram | Удобно из канала | Нет TG / смена аккаунта |
| **Оба входа (TG + email‑OTP)** | Если почта лежит — вход через TG и наоборот | Нужны виджет TG и SMTP |

**Цель плана:** оба способа на одном аккаунте; пароль не обязателен. Email‑OTP: короткий TTL, rate limit, кнопка «отправить снова». Пока SMTP нет — UI/API OTP можно заложить, отправку включить на шаге почты.

### Третьи лица (auth)

1. Telegram — идентификатор и имя из виджета (указать в политике).
2. Почта — только адрес + код, без ДР.

## Политика (минимальная версия)

1. Бренд сервиса.
2. Оператор: физлицо, самозанятый.
3. Контакт для ПДн: email (плейсхолдер до почты на домене).
4. Состав: email и/или Telegram id, имя, ДР, карты, чаты.
5. Цели: аккаунт, расчёт карт, ИИ‑тексты.
6. Третьи: Astrology API; ИИ (без ДР); DaData (поиск города); Telegram (вход); почтовый сервис (коды).
7. Права: доступ, исправление, удаление аккаунта.
8. Согласие — чекбокс при первой регистрации (и TG, и email).

## Домен и URL

1. Покупка — в конце.
2. Публичный URL: env `APP_BASE_URL` (пример `https://104.x.x.x` → потом `https://example.ru`).
3. В политике и письмах ссылаться на `APP_BASE_URL`, не хардкодить домен.
4. Кандидаты на потом: `.ru` — `mynatal.ru`, `astrokart.ru`, `natalkarta.ru`.

## Итерации (порядок шагов)

Сначала продукт и тексты. Домен, РФ‑сервер, SMTP — в конце.

### Шаг 1 — политика и согласие
1. Страница `/privacy` (минимальный текст выше).
2. Чекбокс согласия на регистрации (TG и email).
3. Контакт ПДн — плейсхолдер email / позже `privacy@…`.

### Шаг 2 — модель User под два входа
1. `telegramId` optional unique; `email` optional unique; `passwordHash` optional.
2. Инвариант: есть telegramId или email.
3. Миграция: текущие пользователи с email+паролем остаются валидны.

### Шаг 3 — вход через Telegram
1. Telegram Login Widget (бот + domain/URL из `APP_BASE_URL` когда появится; до домена — IP/временный URL в настройках бота).
2. API: проверка подписи виджета → найти/создать User → JWT cookie.
3. Согласие при первом создании через TG.

### Шаг 4 — email без обязательного пароля
1. Запрос кода на email (OTP) → проверка → сессия.
2. Привязка email к уже залогиненному через TG; привязка TG к уже залогиненному через email.
3. Пока SMTP нет: интерфейс + хранение OTP; реальная отправка — на шаге 8 (или тестовый лог только в dev).
4. Старый вход паролем: оставить для существующих или убрать после миграции на OTP+TG — **открытый вопрос** (рекомендация: оставить пароль как опцию, не требовать).

### Шаг 5 — удаление аккаунта
1. Удалить User + карты + наложения + связанные записи.
2. Ссылка из политики / профиля.

### Шаг 6 — ИИ без ДР
1. Убрать `birthInput` из промптов чата/интерпретаций.
2. В контексте — планеты, дома, аспекты.

### Шаг 7 — домен (позже)
1. Купить домен; выставить `APP_BASE_URL=https://<domain>`.
2. Обновить URL бота Telegram Login.
3. Подставить домен в `/privacy`.

### Шаг 8 — почта SMTP (позже)
1. Ящики `noreply@` / `privacy@` на домене (Yandex 360 / аналог).
2. Включить реальную отправку OTP.
3. Письма: только код/ссылка, без ДР.

### Шаг 9 — РФ‑VPS (позже)
1. Купить VPS в РФ; app + Mongo там.
2. HTTPS на `APP_BASE_URL`; выключить старый не‑РФ после проверки.
3. Обновить CI‑секреты и `deployment.md`.

### Шаг 10 — РКН (после выбора A/B/C)
1. A — уведомление по факту после шагов 1 и 9.
2. B — заключение юриста вне репо.
3. C — сначала 1–9, потом A или B.
