## Auth: Telegram + изменения входа (зафиксировано, не в этом PR)

### Сущность User (цель)

- `telegramId` — optional, unique sparse.
- `email` — optional, unique sparse.
- `passwordHash` — optional.
- Нужен хотя бы `telegramId` или `email`.
- Имя / birthPreferences — как сейчас.
- Миграция: текущие email+пароль остаются валидны; пароль — опция, не требование.

### Связь способов

1. Telegram Login Widget → проверка подписи → найти/создать User → JWT.
2. Email → OTP на почту → сессия (SMTP на шаге 8; до этого — закладка API).
3. В профиле: «Привязать Telegram» / «Привязать email» к текущему User.
4. Конфликт id/email у другого User — ошибка, без автослияния.
5. Согласие с `/privacy` при первом создании через TG или email.

### Почему не только код на почту

Сбои/спам почты → «не входят». Telegram из канала компенсирует. Оба способа на одном аккаунте — целевая схема.

### Порядок реализации auth (когда скажете «делай»)

1. Шаг 2 — схема User.
2. Шаг 3 — Telegram Login на сайте (`BOT_TOKEN`, domain/`APP_BASE_URL`).
3. Шаг 4 — email OTP + привязки; пароль оставить опцией для старых.
4. Шаг 11 — Mini App (после 2–3; можно параллельно с 4).

## Telegram Mini App — что это

Не отдельный нативный «апп в сторе». Это **ваш же веб‑UI**, открытый **внутри Telegram** (кнопка в боте / меню / ссылка из канала).

Как работает:

1. В BotFather — бот + пункт Menu Button / Web App URL = `APP_BASE_URL` (или `/tg`).
2. Пользователь в Telegram нажимает → открывается WebView с вашим сайтом.
3. Telegram передаёт `initData` (подпись + user id) — сервер проверяет → тот же User / JWT, что и на сайте.
4. Карты, профиль, ИИ — те же API (`/api/...`), та же Mongo.
5. Снаружи по-прежнему обычный сайт в браузере.

Отличие от шага 3 (Login Widget):

| | Login Widget (шаг 3) | Mini App (шаг 11) |
|--|---------------------|-------------------|
| Где | Кнопка «Войти через Telegram» на сайте | Весь UI внутри Telegram |
| Auth | Виджет → telegramId | `initData` → telegramId |
| Зачем | Войти на сайт из браузера | Пользоваться из канала/бота без отдельного браузера |

Нужны: HTTPS + стабильный URL (удобнее с доменом, шаг 7); тот же `BOT_TOKEN`.

Ограничения Mini App: WebView Telegram, свои кнопки/тема через Telegram JS SDK; email‑OTP внутри TG менее удобен — основной вход = telegramId.

## Домен `.ru`

1. Покупать `.ru` можно (самозанятая в РФ — обычный регистратор: Reg.ru, Timeweb и т.п.).
2. `.ru` ≠ локализация ПДн: DNS на латвийский IP не делает БД «российской».
3. После покупки: A → `104.253.18.4`, HTTPS (обычный LE 90 дней), `APP_BASE_URL=https://<domain.ru>`, обновить Login/Mini App URL у бота.
4. Почта на домене (`noreply@` / `privacy@`) — по-прежнему шаг 8.

## РФ‑VPS: минимум по сложности (отложен)

Сейчас prod остаётся на LV. Перенос — когда решите закрывать риск локализации.

Ориентир (~2 ГБ, без Langfuse):

| Параметр | Минимум | Комфортнее |
|----------|---------|------------|
| RAM | **2 ГБ** | 4 ГБ |
| vCPU | 1–2 | 2 |
| Диск | 20–40 ГБ SSD | 40 ГБ |
| ОС | Ubuntu 22.04 | то же |
| Состав | Docker: app + Mongo 7 | то же |
| Сеть | публичный IPv4 | + домен позже |

1. Не брать 1 ГБ — Mongo + Next часто упираются.
2. Langfuse на этом тарифе не поднимать.
3. Сборка образа — в CI (как сейчас), на VPS только `pull` + compose.
4. Провайдеры РФ (на выбор): Timeweb, Selectel, Reg.ru VPS, Beget — регион РФ обязателен для локализации ПДн.
5. Сложность переноса: скопировать `.env`, `docker-compose.prod.yml`, том/дамп Mongo, nginx+HTTPS; обновить `PROD_SSH_*` в GitHub Secrets.
