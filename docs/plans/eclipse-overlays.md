# Наложения натальных карт и карт затмений

**Статус:** реализация подготовлена в текущем PR по явному поручению пользователя; merge/deploy не выполнялись.  
**Страница:** «Наложения», `/overlays`.  
**Порядок работы:** эта спецификация → PR с документацией → реализация только после отдельного явного «делай» пользователя. Разрешение на подготовку спеки или PR не означает разрешения на реализацию, merge или deploy.

## Задача

Пользователь выбирает свою сохранённую натальную карту и затмение. Приложение вычисляет межкартные аспекты, сохраняет расчёт, получает расшифровку ИИ и позволяет обсудить весь результат или отдельный аспект. Повторное открытие работает по сохранённым данным, без повторного обращения к Astrology API.

## Согласованные требования

### Каталог затмений

- Первоначально загрузить все солнечные и лунные затмения 2026 и 2027 годов, включая частные и полутеневые.
- Использовать точный момент максимума затмения. Хранить UTC, тип события, источник даты/времени и точность времени. Перед загрузкой проверить шкалу времени источника: TD/TT нельзя сохранять под видом UTC; UT также требует явного описания точности.
- Рассчитать геоцентрические положения тел в тропическом зодиаке. Карта затмения общая для всех пользователей; дома затмения не нужны.
- Сохранить исходный ответ Astrology API и нормализованные абсолютные долготы. Положения каждого затмения получать один раз и повторно использовать.
- Для самой карты затмения не вызывать ИИ: ни построение API payload, ни описание не требуют AI-интерпретации.
- Можно добавлять новые затмения. Редактирования существующих затмений в первой версии нет.
- До ролевой модели добавление доступно авторизованным пользователям. В будущем — только администратору; задача записана в backlog.
- Способ назначения администратора, в том числе через защищённый API, пока не выбран.

### Выбор натальной карты

- Можно выбрать основную или любую другую сохранённую карту текущего пользователя.
- Использовать сохранённые положения, а не заново строить натальную карту.
- После смены основной карты старое наложение остаётся привязано к конкретной ранее выбранной карте.
- Недоступные и неполные исходные данные показывать как ошибку/неготовность, не подменять нулями.

### Аспекты

Участвуют Солнце, Луна, Меркурий, Венера, Марс, Юпитер, Сатурн, Уран, Нептун, Плутон, Северный и Южный узлы. Узлы участвуют наравне с планетами. ASC, MC, Лилит, Хирон и астероиды в расчёт не включать.

Использовать средний Северный узел, как в существующем представлении карт проекта; Южный — противоположная точка (+180°). Истинный узел дополнительно не включать.

| Аспект | Точный угол | Допустимый орбис |
|--------|-------------|-----------------|
| Соединение | 0° | ≤ 5° |
| Секстиль | 60° | ≤ 5° |
| Квадрат | 90° | ≤ 5° |
| Трин | 120° | ≤ 5° |
| Оппозиция | 180° | ≤ 5° |

- Проверять все пары: одно тело натальной карты × одно тело карты затмения. Учитывать разные и одинаковые названия тел.
- Расчёт выполняется внутренним кодом, без ИИ и дополнительных внешних API.
- Для долгот a и b в [0°, 360°): d = min(|a − b|, 360° − |a − b|); орбис = |d − точный угол аспекта|.
- Сравнивать неокруглённые числа. Округление применять только для отображения.
- Граница знаков не препятствует аспекту: 359° и 2° дают соединение с орбисом 3°.
- Сохранить идентификаторы тел и принадлежность к каждой карте, долготы, угловое расстояние, тип аспекта и орбис.
- Сортировать по возрастанию орбиса. При равном орбисе использовать стабильный порядок тел и типов.
- Северный и Южный узлы не объединять: это отдельные точки, даже если аспекты образуют связанные пары.
- Если аспектов нет: сохранить пустой результат, показать сообщение и автоматически не вызывать ИИ для расшифровки.

### Страницы

В меню рядом с «Мои карты» добавить пункт «Наложения».

`/overlays`:
- Кнопка «Новое наложение».
- Список сохранённых наложений текущего пользователя.
- Для каждого результата: выбранная карта, дата и тип затмения, число аспектов и состояние готовности.
- Переход к сохранённому результату и чату.

Форма нового наложения:
- Выбор своей основной/обычной карты.
- Выбор затмения из каталога.
- Явный запуск создания результата.

Страница результата (предлагаемый путь `/overlays/[id]`):
- Данные выбранных карт и затмения, таблица аспектов по точности.
- Расшифровка, действие «Обновить расшифровку», чат.
- У каждой строки аспекта действие «Обсудить»: выбрать аспект и задать вопрос в чате.
- Ошибку ИИ можно повторить без повторного вызова Astrology API и потери аспектов.
- Фильтров нет. Графическое колесо и отображение натальных домов в объёме первой версии не согласованы и не включаются.

### Расшифровка ИИ

- Передавать данные натальной карты, дату/тип затмения, положения карты затмения и точный рассчитанный список аспектов.
- Формат: общий обзор → объяснение найденных аспектов с указанием тел обеих карт и орбисов → итог.
- Источник фактов — расчёт приложения. ИИ не должен добавлять аспекты, которых нет в рассчитанном списке.
- Сохранить ответ в БД и показывать его при повторном открытии.
- «Обновить расшифровку» строит новый запрос по сохранённым исходным данным, без старого текста расшифровки; Astrology API не вызывается.
- При неудачном обновлении не терять предыдущую успешную расшифровку.

### Чат

- Отдельная сохраняемая переписка для каждого наложения.
- Контекст: данные обеих карт, рассчитанные аспекты, текущая сохранённая расшифровка, история переписки и выбранный для обсуждения аспект.
- Расшифровка передаётся как предыдущая интерпретация, которую можно пересмотреть, а не как доказанный факт.
- При обсуждении конкретного аспекта передавать его устойчивый идентификатор; на сервере проверять принадлежность этому наложению.
- Сохранять вопросы и ответы. Повторное открытие восстанавливает чат.
- Чат и обновление расшифровки не запрашивают положения у Astrology API.

## Предлагаемая техническая схема

Это проект реализации, а не уже существующие модели/эндпоинты.

### Факты существующего кода

- Next.js, MongoDB/Mongoose; User → Client → ChartRequest/ChartResult.
- Основная карта хранится с `isPrimary`.
- Сырые данные содержат `fullDegree`; таблица UI хранит градус внутри знака, текст промпта округлён. Для аспектов нужны абсолютные долготы.
- `buildApiPayload` уже детерминированный, несмотря на старое описание в основной спеке.
- `fetchPlanets` можно вызвать отдельно; общий `runChartPipeline` запрашивает также дома и интерпретацию, поэтому не подходит для затмений без выделения отдельного пути.
- В модели User роли пока нет.
- Существующие моки возвращают фиксированную карту 1984 года. Нельзя сохранять её как реальные данные затмения, если нет API-ключа или включён mock-режим.

### Хранение и повторное использование

Предлагается две отдельные модели:

1. `Eclipse`: тип, момент максимума UTC, источник и исходная шкала времени, статус получения положений, сырые и нормализованные положения, версия расчётной конфигурации, автор добавления, ошибка и timestamps.
2. `Overlay`: владелец, ссылки на натальную карту и затмение, снимки использованных положений/метаданных, конфигурация аспектов, рассчитанные аспекты, расшифровка, чат, состояния операций и timestamps.

Снимок обеспечивает читаемость сохранённого результата, если исходная натальная карта позже удалена или пересчитана. Новые наложения можно создавать только по доступным картам владельца.

- Пара `userId + natalChartId + eclipseId + calculationVersion` должна быть уникальна: повторное создание возвращает сохранённый результат.
- Каталог наполнять идемпотентно; повторная загрузка не создаёт дубликаты.
- Для получения данных затмения применять атомарный захват задачи/блокировку: параллельные запросы не должны одновременно обращаться к Astrology API за одним событием.
- Завершённые данные не обновлять при чтении. Повтор внешнего вызова допустим лишь после явной ошибки/незавершённого получения, когда корректных сохранённых данных ещё нет.
- Отделить состояния расчёта и ИИ: ошибка интерпретации не превращает успешный расчёт аспектов в потерянный результат.
- Права на результат, чат и все действия проверять на сервере по текущему пользователю.
- Каталог общий; личные результаты и чаты другим пользователям не отдавать.

### Предлагаемые API

| Метод/путь | Назначение |
|------------|------------|
| GET /api/eclipses | Каталог сохранённых затмений |
| POST /api/eclipses | Добавление нового события после авторизации |
| GET /api/overlays | Личные сохранённые наложения |
| POST /api/overlays | Создать/найти результат выбранной пары |
| GET /api/overlays/[id] | Сохранённые аспекты, расшифровка, история чата |
| POST /api/overlays/[id]/reinterpret | Новая независимая расшифровка из сохранённого расчёта |
| POST /api/overlays/[id]/ask | Вопрос по наложению/выбранному аспекту |

Редактирование и удаление затмений/наложений не добавлять в объём этой задачи. Первоначальную загрузку каталога реализовать отдельным идемпотентным действием/скриптом; не выполнять заполнение и внешние API-вызовы автоматически при открытии списка.

Конкретные имена моделей, маршруты страницы создания и способ выполнения длительных задач можно уточнить при реализации, сохраняя согласованное поведение.

## Что проверить при реализации

- Все пять типов аспектов, одинаковые и разные тела, Северный/Южный узлы.
- Переход 359° → 2°, ровно 5°, чуть больше 5°, отсутствие аспектов, некорректные долготы.
- Использование исходной точности, стабильная сортировка, исключение лишних тел.
- Каталог 2026/2027 сверён с первичными источниками; время переведено корректно, секунды не теряются.
- Повторное наполнение, создание той же пары и параллельные запросы не создают дубликаты.
- Открытие списка/результата, чат и обновление расшифровки не вызывают Astrology API.
- Одно затмение повторно используется для нескольких карт/пользователей без нового запроса положений.
- Пустой набор аспектов не запускает автоматическую расшифровку.
- Ошибка ИИ позволяет повторить запрос без потери исходных данных, аспектов и прежнего успешного ответа.
- Чужие карты, результаты, сообщения и аспекты недоступны.
- Смена основной/удаление исходной карты не уничтожают сохранённую историю наложения.
- Выбор строки «Обсудить» сохраняет принадлежность тел к картам.
- Отсутствие реального API-ключа не записывает моки как астрономические данные.
- Проверка типов/сборка и необходимые проверки поведения. В PR отдельно указать ограничения реально выполненной валидации.

## Не входит в текущую поставку

- Ролевая модель и назначение администратора: отдельная задача backlog.
- Фильтры, колесо двух карт, показ натальных домов, сравнение всех затмений сразу.
- Редактирование существующих затмений и история их версий.
- Merge, запуск workflow деплоя, SSH и действия на сервере.

## План реализации (разрешение «делай» получено)

1. Проверить точные времена и источники каталога; подготовить данные.

3. Реализовать расчёт аспектов и сохранение наложений.
4. Добавить интерпретацию и сохраняемый чат.
5. Добавить страницы и пункт меню «Наложения».
6. Проверить поведение, создать отдельную ветку/PR реализации. Не выполнять merge/deploy.
